# Agent response report

The report measures completed human replies. First response is the time from the first inbound message awaiting a human reply to the first successful human reply in a confirmed open cycle. A close and subsequent confirmed reopen starts a new cycle. A message received while closed does not itself prove reopening; a reply while still closed counts toward waiting time, but not first response. Waiting time averages each completed waiting block, starting with the first unanswered inbound and ending with the next successful human reply. Repeated inbound messages do not restart the timer; automated and failed messages do not stop it. Unanswered blocks are excluded. A response is attributed to the person who sent it and to the reporting period containing the response, in the organization's timezone. Open and closed counts are the current tickets assigned to each agent, not counts of events in the selected period.

With business hours on, the duration is the union of scheduled working intervals in the organization's timezone; the configured end is exclusive. The legacy 00:00–23:59 schedule is treated as a full day to preserve existing automation behavior. Invalid, disabled or missing schedules use elapsed time and the report displays a notice. An invalid or missing schedule also makes the automated greeting eligible rather than the away trigger. An active day must have valid start and end times; overnight periods continue into the next day. Schedule changes saved through organization settings are versioned, and an interval spanning a change is split at the change time.

Historical limitations: the system retains textual status events and message timestamps with second precision. Old duplicate, missing, delayed or incorrect events cannot be repaired reliably from those records. After the link migration, new webhook-triggered openings and reopens store the triggering chat ID; older unlinked events retain their recorded time and cannot establish a cycle earlier than that event. Until migration the system remains operational but cannot save links. When no linked opening exists, the first inbound in the five minutes before ticket creation is treated as the trigger; this is an approximation. A valid WhatsApp provider timestamp is used for inbound duration and ordering, while database query boundaries still use processing timestamps. When available, unified chat log IDs break same-second ties; otherwise deterministic ordering is used and may differ from the real sequence. Before the first recorded schedule change the previously configured schedule is used as a baseline, not a verified history. Assignment-based metrics cannot be reconstructed reliably from the current data. Review old records before using the report as an SLA or payroll source.

The implementation fetches message and event history in batches of 200 contacts. It still reconstructs historical cycles at request time, so installations with very large histories should benchmark it and consider a versioned event and precomputed metrics store. New status changes and their event records are written together in the manual UI/API paths. Awaiting Reply is the number of unanswered conversations at the report end attributed to the current assignee; it includes closed conversations with an unanswered message and excludes unassigned ones.
