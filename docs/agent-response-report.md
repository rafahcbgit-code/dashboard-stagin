# Agent response report

The report measures completed human replies. First response is the time from the first inbound message awaiting a human reply to the first successful human reply in an open cycle. A close and subsequent reopen starts a new cycle. Waiting time averages each completed waiting block, starting with the first unanswered inbound and ending with the next successful human reply. Repeated inbound messages do not restart the timer; automated and failed messages do not stop it. Unanswered blocks are excluded. A response is attributed to the person who sent it and to the reporting period containing the response, in the organization's timezone. Open and closed counts are the current tickets assigned to each agent, not counts of events in the selected period.

With business hours on, the duration is the union of scheduled working intervals in the organization's timezone; the configured ending minute is inclusive. Invalid, disabled or missing schedules use elapsed time and the report displays a notice. An invalid or missing schedule also makes the automated greeting eligible rather than the away trigger. An active day must have valid start and end times; overnight periods continue into the next day.

Historical limitations: the system retains one ticket per contact, textual status events, and message timestamps with second precision. Old duplicate, missing, delayed or incorrect events cannot be repaired reliably from those records. When available, unified chat log IDs break same-second ties; otherwise deterministic ordering is used and may differ from the real sequence. Historical changes to business hours and timezone are not versioned, so historical metrics use the current configuration. Assignment-based metrics cannot be reconstructed reliably from the current data. Review old records before using the report as an SLA or payroll source.

The implementation fetches message and event history in batches of 200 contacts. It still reconstructs historical cycles at request time, so installations with very large histories should benchmark it and consider a versioned event and precomputed metrics store. New status changes and their event records are written together in the manual UI/API paths.
